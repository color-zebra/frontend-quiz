# Теория ядра собеседования: план вопросов и промпт для сессии

## Зачем

База сильна в задачах «что выведется в консоль», но почти не объясняет сами механизмы. Подсчёт на 2026-10-13
(«теория» — вопросы без кода, «что это и как устроено»):

| Тема | Теория / всего | Провалы |
|---|---|---|
| JavaScript | 36 / 183 | scope — 0, classes — 0, objects — 0, prototypes — 1, closures — 2, this — 2, event-loop — 2 из 14 |
| TypeScript | 11 / 124 | в 7 подтемах из 11 теории ноль |
| React | 23 / 111 | state — 1 из 11, effects — 2 из 13 |
| HTML и CSS | 31 / 72 и 43 / 101 | cascade — 2 из 11, box-model — 2 из 12 |
| Сети, Next.js | 62 / 69 и 64 / 80 | тестовой теории хватает — только устные (этап 5) |

Устных вопросов (`speech/`) нет ни одного.

Цель: чтобы по каждой подтеме ядра можно было **понять механизм с нуля** — сначала теория «что это и как устроено»,
потом уже задачи на код, которые в базе есть.

## Промпт для новой сессии

Скопируй блок ниже целиком в новую сессию Claude Code, открытую в `E:\frontend-quiz`.

````text
Ты пополняешь базу вопросов Zubrilka в E:\frontend-quiz теоретическими вопросами по ядру фронтенд-собеседования.
План — в E:\frontend-quiz\plans\theory-core.md, раздел «Список вопросов». Работаем ЭТАПАМИ, по одному: сейчас этап,
который я назову (по умолчанию — Этап 1, ядро JavaScript).

Прочитай перед началом:
- README.md — разделы «Формат вопроса», «Устные вопросы», «Правила». Это обязательные правила базы.
- topics.yaml — темы и подтемы; файлы лежат в questions/<тема>/<подтема>.yaml и speech/<тема>/<подтема>.yaml.
- Файлы подтем этапа целиком: прежде чем писать вопрос, убедись, что такого (даже другими словами) ещё нет.

Что писать:
1. Тестовые теоретические вопросы — по пунктам «Список вопросов». Пункт — это ТЕМА вопроса, а не готовая
   формулировка: формулировку, варианты и why пишешь ты. Пункт можно разбить на два вопроса или объединить
   с соседним, если так честнее.
2. Устные вопросы — по пунктам «Устные» в каждой подтеме, в speech/<тема>/<подтема>.yaml (папки speech/ пока нет —
   создай). answer — эталонный ответ хорошего кандидата на собеседовании: 5–10 предложений, живым языком, с мини-
   примером кода, если без него непонятно. points — 3–6 тезисов, которые обязательно стоит упомянуть.

Правила (сверх README):
- Теория без кода или с минимальным кодом (2–5 строк иллюстрации), вопрос проверяет понимание механизма, а не
  память на синтаксис. Задачи «что выведется» НЕ пишем — их в базе достаточно.
- Не дублировать: ни существующие вопросы базы, ни друг друга. Если механизм уже проверен задачей на код —
  теоретический вопрос всё равно нужен, но спрашивать «почему так», а не повторять ту же ситуацию.
- 30–40 % новых тестовых вопросов — с несколькими правильными ответами («какие из утверждений верны»), по правилам
  README. Каждый вариант однозначно верен или неверен сам по себе.
- В каждой подтеме после добавления — все три уровня (junior, middle, senior); новые вопросы распределяй так,
  чтобы теория была на всех уровнях: junior — «что это», middle — «как устроено», senior — тонкости и подвохи.
- Правильный ответ не угадывается по форме: варианты одинаковой формы и сопоставимой длины. Пояснения к НЕВЕРНЫМ
  вариантам — главный источник ошибок: их факты проверяй так же строго, как ответ.
- Факты — по спецификации и MDN. Если в варианте есть утверждение о поведении кода — проверь его запуском:
  node scripts/run-js.mjs / run-ts.mjs / run-react.mjs (см. README, раздел «Команды»).
- id — следующий свободный номер в подтеме (<тема>-<подтема>-NNN; у устных speech-<тема>-<подтема>-NNN),
  старые id не трогать и не переиспользовать.
- links — MDN, спецификация, react.dev, typescriptlang.org; source: own.
- Язык — русский, термины и код — на английском.

Процесс:
1. Пишешь вопросы подтемы за подтемой. После каждой подтемы — pnpm check (ноль ошибок, предупреждения о перекосах
   длины разобрать).
2. Когда этап написан — агент-скептик проверяет его: фактические ошибки (в ответах И в why неверных вариантов),
   дубли с существующей базой, угадываемость ответа, спорные варианты в вопросах с несколькими ответами, понятность.
   До двух итераций скептика на этап. ПЕРЕД запуском агентов скажи мне, сколько их и примерную стоимость
   в токенах, и дождись «го».
3. Правки по скептику, pnpm check, pnpm build.
4. Отчёт: сколько вопросов добавлено по подтемам, что поправил скептик. Коммит делаю я сам — git не трогай.

Нельзя: заглядывать в E:\СОБЕСЫ 2026\ и E:\Вопросики.txt; rm -rf; npm/yarn (только pnpm); менять код приложения.
````

Reconciliation:
- Почему React не ищет минимальную разницу «честно», а опирается на две эвристики — тип элемента и `key` (middle).
- Элемент другого типа на том же месте (`<div>` → `<section>`, `A` → `B`): поддерево уничтожается вместе с состоянием (middle).
- Компонент, объявленный внутри другого компонента, теряет состояние на каждом рендере: новая функция = новый тип (senior).
- Что сбрасывает состояние (тип, `key`, позиция), а что нет (новые пропсы, ре-рендер родителя, `memo`) (middle, несколько).
- Где живёт состояние `useState`: в узле дерева, привязано к позиции; отсюда правило порядка хуков (junior).

Fiber:
- Какую проблему решал Fiber в React 16: непрерываемый рекурсивный рендер → работа маленькими единицами (junior).
- Элемент React против Fiber-узла: одноразовое неизменяемое описание против долгоживущего объекта экземпляра (middle).
- Что хранит Fiber-узел: состояние хуков, ожидающие обновления, ссылку на DOM-узел, связи с родителем, ребёнком и
  соседом, пометки для коммита; НЕ копию DOM и НЕ HTML (middle, несколько).
- Почему дерево связано ссылками «ребёнок → сосед → родитель», а не обходится рекурсией: можно остановиться и
  продолжить с любого узла (middle).
- Две версии дерева (на экране и черновая): можно начать, отложить, выбросить работу; после коммита меняются ролями (middle).
- Что можно прервать (рендер в конкурентном режиме), а что нет (коммит — синхронно и целиком) (middle, несколько).
- Рендер только помечает узлы («вставить, обновить, удалить»), коммит применяет пометки одним проходом — поэтому DOM
  меняется целиком, а не по частям (middle).
- Почему один тяжёлый компонент тормозит даже в переходе: уступить браузеру можно только между узлами (senior).
- Как React пропускает неизменившееся поддерево и почему помогает приём «передать через `children`»; задача на
  эффект уже есть (react-memo-007), здесь — теория «почему» (senior).
- Защита от «голодания»: отложенная работа со временем становится срочной (senior).
- Что стало возможным благодаря Fiber: прерываемый рендер и приоритеты, Suspense, границы ошибок, фрагменты и
  массивы; НЕ хуки как таковые и НЕ JSX (middle, несколько).

Конкурентный рендер и приоритеты:
- «Конкурентный» — не многопоточность, а возможность приостановить одну работу и переключиться (middle).
- Срочные (ввод, клики) и несрочные (переходы, отложенные значения) обновления; что происходит с несрочным рендером
  при срочном обновлении (middle, несколько). Не дублировать react-rendering-009 (рендер выбрасывается).
- Почему обновление значения управляемого поля нельзя оборачивать в `startTransition` (senior).
- Почему React продолжает работу задачей, а не микрозадачей — связь с event loop из этапа 1 (senior).
- Tearing и зачем `useSyncExternalStore` в конкурентном режиме (senior).

Батчинг:
- Что такое батчинг и зачем (junior).
- Батчинг в React 18 против 17: `setTimeout`, промисы, нативные обработчики (middle).

Suspense и гидратация:
- Как Suspense работает концептуально: «данных нет» → ближайший fallback → рендер заново с начала компонента (middle).
  Не дублировать react-concurrent-007 (новый промис в `use` на каждый рендер).
- Гидратация и почему расхождение серверного и клиентского HTML — ошибка (`Date.now()`, `Math.random()`, `window`) (middle).
- Выборочная гидратация (React 18): границы Suspense гидратируются независимо, первой — та, где кликнули (senior).

Устные: «Что такое Fiber и зачем его ввели?»; «Что хранит Fiber-узел и как React понимает, какую часть дерева можно не
перерисовывать?»; «Как React понимает, что изменилось: reconciliation и ключи»; «Что такое конкурентный рендер и как
React расставляет приоритеты?»; «Как работает Suspense?».

- В какой версии появились хуки — 16.8, 2019 (junior).
- Что принёс React 16 вместе с Fiber: фрагменты, порталы, границы ошибок, массивы и строки из рендера (middle, несколько).
- Современный Context API (`createContext`), `createRef`, `forwardRef` — 16.3 (middle).
- `memo`, `lazy`, `Suspense` для разделения кода — 16.6 (middle).
- React 17 «без новых возможностей»: события на корне вместо `document`, новый JSX-трансформ без `import React`,
  асинхронная очистка эффектов (middle, несколько).
- Зачем в 17 делегирование перенесли на корень: несколько версий React на странице, постепенные обновления (senior).
- `createRoot` и автоматический батчинг — 18 (junior).
- Что появилось в 18: переходы, `useDeferredValue`, `useId`, `useSyncExternalStore`, потоковый SSR с Suspense (middle, несколько).
- StrictMode в 18: двойное монтирование эффектов в разработке и зачем (middle).
- Что появилось в 19: Actions, `useActionState`, `useOptimistic`, `useFormStatus`, `use`, `ref` как проп, Context
  как провайдер, метаданные документа (middle, несколько).
- Что в 19 удалено (`propTypes`/`defaultProps` у функций, строковые refs, `ReactDOM.render`), а что лишь устарело
  (`forwardRef`) (senior, несколько).
- Когда серверные компоненты стали стабильными — 19 (senior).
- `<Activity>` и `useEffectEvent` — 19.2, октябрь 2025 (middle).
- React 19.3 (сентябрь 2026): стабильные `<ViewTransition>` и Fragment Refs, переходы рендерятся независимо (senior).
- Хронология: хуки → `createRoot` → Actions → `<Activity>` (junior).
- Возможно: React Compiler 1.0 (октябрь 2025) — с какими версиями React работает; факт проверить при написании.
