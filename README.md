# Frontend Quiz — база вопросов для подготовки к собеседованиям

Вопросы с вариантами ответов по фронтенду. На каждый вариант есть пояснение, почему он верен
или неверен, а у каждого вопроса — общее объяснение механизма. Поверх базы сделано приложение для
тренировки Zubrilka (папка `app/`), оно опубликовано на https://color-zebra.github.io/frontend-quiz/.

## Структура

```
topics.yaml                         — темы и подтемы с русскими названиями
questions/<тема>/<подтема>.yaml     — вопросы одной подтемы
schema.json                         — схема файла вопросов (подсказки в VSCode)
scripts/check.mjs                   — проверка базы и сборка в JSON
scripts/run-js.mjs                  — выполняет код JS-вопросов и печатает реальный вывод рядом с ответом
scripts/lengths.mjs                 — показывает вопросы, где правильный вариант заметно длиннее остальных
dist/questions.json                 — собранная база (создаётся командой build, в гит не попадает)
app/                                — приложение для тренировки, см. app/README.md
design/                             — макеты четырёх тем оформления на голом HTML и CSS
examples/                           — пример своего набора вопросов и описание его формата
```

## Команды

```
pnpm install     — один раз, ставит зависимости базы и приложения
pnpm dev         — запустить приложение локально (нужен собранный dist/questions.json)
pnpm app:build   — собрать базу и приложение, как при деплое
pnpm password <пароль>   — задать пароль на вход в приложение (--off — без пароля), потом закоммитить
pnpm check       — проверить базу и показать, сколько вопросов каждого уровня в каждой подтеме
pnpm build       — проверить и собрать dist/questions.json
node scripts/run-js.mjs questions/javascript/event-loop.yaml [id]   — сверить ответы с реальным выводом Node
```

`run-js.mjs` выполняет код как обычный браузерный скрипт (не модуль). Вопросы, которые так не запустить
(DOM, модули из нескольких файлов, сеть), помечены тегом `no-run` и пропускаются.

```
node scripts/run-ts.mjs questions/typescript/generics.yaml [id]     — ошибки компилятора и вывод TS-кода
node scripts/run-react.mjs questions/react/effects.yaml [id] [сценарий.mjs]   — вывод консоли React-кода
node scripts/reflow.mjs questions/network/*.yaml   — заново перенести строки в question/explanation (ширина 110)
```

- `run-ts.mjs` компилирует код в режиме `strict` (TypeScript из devDependencies) и печатает ошибки с номерами
  строк, затем запускает результат как ES-модуль. Настройки компилятора переопределяются комментарием в
  начале кода: `// @noUncheckedIndexedAccess: true` — он же показывает читателю, при каких настройках вопрос.
- `run-react.mjs` выполняет код в jsdom на React из devDependencies. Импорты из `react` в коде вопроса
  опускаются, скрипт подставляет их сам. Компонент `App` без своего `render` монтируется в `#root` без
  StrictMode. Клики и ввод проверяются сценарием: ESM-файл, чья default-функция получает `{ document, window,
  sleep, flushSync }`. Сценарии в базе не хранятся.

## Как правка попадает в приложение

1. Правишь YAML — локально или прямо на GitHub (на странице репозитория клавиша `.` открывает редактор).
2. Пуш в `main` запускает GitHub Actions (`.github/workflows/deploy.yml`): проверка базы, сборка
   `questions.json` и приложения, выкладка на GitHub Pages. Если `pnpm check` находит ошибку, деплой
   не идёт и на сайте остаётся прошлая версия. Ход сборки — во вкладке Actions репозитория.
3. Через минуту-две в приложении нажимаешь «Обновить» на главной.

Перед пушем полезно прогнать `pnpm check` локально, чтобы не ждать, пока ошибку найдёт GitHub.

## Формат вопроса

```yaml
- id: html-forms-007          # <тема>-<подтема>-NNN
  level: middle               # junior | middle | senior
  tags: [forms, validation]   # необязательно
  question: |
    Текст вопроса. Можно Markdown: `код`, **жирный**.
  code: |                     # необязательно — код к вопросу без ```-обёртки
    <input required disabled>
  codeLang: html              # обязателен, если есть code: html|css|scss|js|ts|jsx|tsx|http|json|text
  multiple: true              # необязательно — галочки при одном правильном варианте (см. правила)
  options:                    # ровно 4 варианта; в вопросе с несколькими ответами — от 4 до 6
    - text: 'Вариант'
      why: 'Почему он неверен'
    - text: 'Правильный вариант'
      correct: true           # у правильного варианта; правильных может быть несколько
      why: 'Почему он верен'
  explanation: |
    Как это устроено — общий механизм, на 3–6 предложений.
  links:
    - https://developer.mozilla.org/...
  source: own                 # own или <репозиторий>#<номер>
```

## Правила

- **id не менять и не переиспользовать.** К нему в приложении привязаны заметки. Удалённый вопрос
  освобождает номер навсегда, новый вопрос берёт следующий свободный номер в подтеме.
- **Правильный ответ помечается флагом `correct: true`, а не номером:** приложение перемешивает
  варианты.
- **Вопросы с несколькими ответами.** Если `correct: true` стоит у нескольких вариантов, приложение показывает
  галочки и подсказку «Выберите все подходящие варианты». Ответ засчитывается, только если выбраны все
  правильные и ни одного лишнего. Вариантов в таком вопросе от 4 до 6, и хотя бы один должен быть неправильным.
  - Поле `multiple: true` включает галочки при одном правильном варианте. Без него вид вопроса подсказывал бы,
    что правильных ответов несколько; с ним «выберите все подходящие» может означать и один ответ.
  - Подходят вопросы вида «какие из утверждений верны», «какие свойства создают …». Вопросы на значение
    («что выведется») остаются с одним ответом.
  - Каждый вариант должен быть однозначно верен или неверен сам по себе: спорный вариант в таком вопросе
    ломает засчёт целиком. `why` объясняет каждый вариант, как и в обычном вопросе.
- **В каждой подтеме должны быть вопросы всех трёх уровней.** В приложении можно выбрать уровень,
  и подтема не должна на нём оказаться пустой.
- **Язык — русский, термины и код — на английском.**
- **Правильный ответ не должен угадываться по форме.** `pnpm check` предупреждает о двух перекосах.
  - Правильный вариант заметно длиннее остальных.
  - Пояснение после тире или двоеточия есть только у правильного варианта или только у неверных.

  Отсюда два правила.
  - В вопросах на значение («что выведется», «какой DOM», «какой файл», «сколько пикселей») варианты —
    голые значения, все обоснования — в `why`.
  - В концептуальных вопросах у всех четырёх вариантов одинаковая форма и сопоставимая длина. Подробности
    правильного ответа переносятся в его `why`.
- **Тексты вариантов — в одинарных кавычках.** YAML не любит двоеточия, решётки и обратные кавычки
  в начале строки, а кавычки снимают проблему. Апостроф внутри пишется двумя: `''`.
- **В VSCode** с расширением YAML от Red Hat первая строка файла
  `# yaml-language-server: $schema=../../schema.json` включает подсказки полей и подсветку ошибок.
